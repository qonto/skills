What does your infra really cost, per user? — everyone knows their MRR; nobody knows their infra unit economics.

🔍 100% read-only, zero writes🧮 €/user measured, never invented 🔌 Multi-MCP detected dynamically📄 PR-ready

🎯 Why this matters

A SaaS founder recites their MRR by heart. Their infra cost per user? Silence. Vercel, Supabase, OpenAI and AWS bills drown in the card debits, and gross margin drifts with nobody watching. The skill answers with what actually left the bank account:

1

Infra debits isolated

Vercel, Supabase, OpenAI, AWS, Scaleway, OVH… recognized at the first occurrence, spellings normalized, grouped by family: cloud, data, AI, observability, tooling.

2

Product telemetry

From connected MCPs: Vercel (projects, deployments), Supabase (projects, users via read-only SELECT count), Sentry optional.

3

True unit economics

€/user, €/project (proration announced), month-by-month gross-margin drift against receipts.

4

The bleeders

Side-projects billed with zero deployments in 90 days, empty databases on paid tiers, AI spend growing faster than users.

Would someone use this on a Monday morning? It's the question every technical founder asks in the shower and never answers.

⚙️ How it works

Holds up on messy data

  • No dictionary to maintain: vendors are identified from Claude's world knowledge at their first invoice — an AI API that launched last month is recognized without any update. Spellings merged (AWS EMEA SARL = AMZN WEB SERVICES = AWS; OPENAI *CHATGPT = OpenAI)
  • Billed in USD, debited in EUR: the skill totals the EUR debit (FX included) and explains why vendor dashboards show a different number
  • Card payments: invoice ↔ debit matching by emitted_at, not settled_at (1–2 day gap)
  • Yearly plans: cadences detected across 24–36 months before any cost is called a "one-off"
  • Ambiguous counterparty (reseller, agency) → asked once, never silently classified
  • No product MCP → announced degraded mode: classification + monthly totals + trend, already useful. No measured count → no €/user, said plainly

🏗 Functional diagram

🔒

100% read-only, on both sides. Qonto side: no write tool is ever called — nothing to approve, nothing executed. Product side: execute_sql is capped at single read-only SELECT count queries, on a table the user confirms before it runs — never DDL/DML, never a guessed table.

🛡 Guardrails

  • Never invents a product metric: no measured count → no €/user, said plainly. Doc examples are fictional and flagged as such
  • Allocation is an editorial choice, shown: every shared-cost proration is announced on the line, never silent
  • Read-only SQL: execute_sql limited to single SELECT count queries on a user-confirmed table
  • Vendor pricing never asserted from memory — the account's numbers, yes; "wrong plan", no
  • Masked IBANs (last 4 digits) · pagination ≤ 50 everywhere · honest degradation
