qonto-infra-margin

Ton infra te coûte combien, par utilisateur ? — le MRR, tout le monde le connaît ; l'unit economics de l'infra, personne.

🔍 100 % lecture, zéro écriture🧮 €/user mesuré, jamais inventé 🔌 Multi-MCP détecté dynamiquement📄 PR-ready

🎯 Le pitch

Un founder SaaS récite son MRR par cœur. Son coût d'infra par utilisateur ? Silence. Les factures Vercel, Supabase, OpenAI, AWS se noient dans les débits carte, et la marge brute dérive sans que personne ne regarde. Le skill répond avec ce qui est réellement sorti du compte :

1

Débits infra isolés

Vercel, Supabase, OpenAI, AWS, Scaleway, OVH… reconnus dès la 1re occurrence, graphies normalisées, classés par famille : cloud, data, IA, observabilité, tooling.

2

Télémétrie produit

Via les MCP connectés : Vercel (projets, déploiements), Supabase (projets, users via SELECT count lecture seule), Sentry en option.

3

Unit economics réel

€/utilisateur, €/projet (prorata annoncé), dérive de marge brute mois par mois face aux encaissements.

4

Les saignées

Side-projects facturés sans déploiement depuis 90 j, bases vides sur palier payant, API IA qui croît plus vite que les users.

⚙️ Fonctionnement global

Ce qui rend le skill robuste sur données sales

  • Reconnaissance sans dictionnaire : les fournisseurs sont identifiés par la culture générale de Claude dès leur première facture — une API IA sortie le mois dernier est reconnue sans mise à jour. Graphies fusionnées (AWS EMEA SARL = AMZN WEB SERVICES = AWS ; OPENAI *CHATGPT = OpenAI)
  • Facturé en USD, débité en EUR : le skill totalise le débit EUR (change inclus) et explique pourquoi les dashboards fournisseurs affichent un autre chiffre
  • Cartes : rapprochement facture ↔ débit par emitted_at, pas settled_at (1-2 j d'écart)
  • Plans annuels : cadences détectées sur 24-36 mois avant de qualifier un coût de « one-off »
  • Tiers ambigu (revendeur, agence) → demandé une fois, jamais classé en silence
  • Pas de MCP produit → mode dégradé annoncé : classification + total/mois + tendance, déjà utile. Pas de comptage mesuré → pas de €/user, dit clairement

🏗 Schéma fonctionnel

🔒

100 % lecture, des deux côtés. Côté Qonto : aucun outil d'écriture appelé, jamais — rien à approuver, rien d'exécuté. Côté produit : execute_sql est bridé à des SELECT count unitaires en lecture seule, sur une table que l'utilisateur confirme avant exécution — jamais de DDL/DML, jamais de table devinée.

🛡 Garde-fous

  • Jamais de métrique produit inventée : pas de comptage mesuré → pas de €/utilisateur, dit clairement. Les exemples des docs sont fictifs et annoncés comme tels
  • Allocation = choix éditorial affiché : tout prorata de coût partagé est annoncé sur la ligne, jamais silencieux
  • SQL en lecture seule : execute_sql limité à des SELECT count unitaires, sur une table confirmée par l'utilisateur
  • Pricing fournisseur jamais affirmé de mémoire — les chiffres du compte, oui ; « mauvais plan », non
  • IBAN masqués (4 derniers chiffres) · pagination ≤ 50 partout · dégradation honnête
