qonto-crew-onboard

One-sentence financial onboarding for every new hire — invitation, capped card, welcome pack.

🗂 Per-role policy, user-decided🔒 Every write confirmed, card behind SCA 🌍 Universal — all Qonto countries❄️ Offboarding = freeze, never delete

🎯 Why this matters

Every new hire triggers the same manual ritual: invite them on Qonto, create their card with the right caps, prepare day one — and every departure triggers the reverse, usually too late. The skill turns both into one sentence:

1

Per-role policy

Defined once with the user — card type, caps, online-only, team per role. Never invented: an unknown role triggers questions.

2

One-sentence onboarding

"Alex starts Monday as a developer": invitation sent, team created if new, a capped card request that conforms to the policy.

3

Multi-MCP welcome pack

Notion page, day-1 Google Calendar event, Gmail draft — when those MCPs are connected; otherwise announced, core continues.

4

Mirror offboarding

"Sam is leaving Friday": cards frozen (reversible) + recovery checklist. Nothing deleted — revocations stay in the app.

Would someone use this on a Monday morning? That's literally when new hires show up.

⚙️ How it works

Holds up on messy data

  • Requester's role checked first: not Admin/Owner → honest warning and a read-only preview of what would be done
  • Emails never guessed: missing from the sentence → asked for; already invited → caught in list_memberships, invitation skipped with the reason
  • Teams matched before creation: "tech" vs "Tech" → no duplicates, create_team only when the team truly doesn't exist
  • Plan member limits: get_subscription returns 403 on the connector → the skill asks the plan, counts members, warns before inviting
  • Notion / Calendar / Gmail MCP absent → one honest line each, the Qonto core continues
  • Offboarding a member with no cards → checklist only, and the skill says exactly what the app must handle · pagination ≤ 50 everywhere

🔒

The security model, not a limitation: reads are risk-free; every write requires explicit confirmation in the conversation. The card is never created directly — create_card_request files a policy-compliant capped request, approved in the Qonto app by an Admin/Owner with their own SCA. And offboarding freezes, it doesn't delete.

🛡 Guardrails

  • Never writes without explicit confirmation: full recap first, then each write (create_membership, create_team, create_card_request, change_card_status) confirmed one by one; a pending request is never presented as done
  • The policy is user-decided, never invented — unknown role = questions
  • Plan member limits: grid not readable (get_subscription 403) → plan asked, members counted, warning before inviting
  • Offboarding never deletes anything: reversible freeze + checklist; definitive revocations in the app
  • Admin/Owner checked first · emails never guessed · pagination ≤ 50 everywhere
