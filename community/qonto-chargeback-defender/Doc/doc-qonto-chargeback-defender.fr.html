qonto-chargeback-defender

Les litiges de paiement bout en bout : détection, débit retrouvé, dossier de défense sourcé, deadline — toi, tu soumets.

✅ Marche en Qonto pur🧾 Pièces sourcées, jamais fabriquées ⏱ Deadlines réelles du litige🌍 Universel — tous pays Qonto

🎯 Le pitch

Un chargeback, c'est triple peine : l'argent repris sur le compte, des frais en plus (souvent 15-20 €, indicatif), et un délai court (7-21 jours) — et la plupart des marchands ne répondent jamais. Le skill transforme le compte Qonto en poste de défense :

1

Litiges détectés

Via le MCP Stripe/PayPal si connecté (motifs, deadlines réelles) ; sinon débits de reprise repérés dans Qonto : dispute / chargeback / reversal + frais.

2

Débit retrouvé

La reprise rapprochée de l'encaissement d'origine : chronologie complète paiement → payout → reprise → frais.

3

Dossier sourcé

Commande Shopify, preuve de livraison, échanges Gmail — chaque pièce avec sa source, les manquantes avec où les trouver.

4

Traçabilité comptable

Mémo de synthèse daté attaché au débit de reprise dans Qonto (upload confirmé) — la transaction porte toute son histoire.

⚙️ Fonctionnement global

Ce qui rend le skill robuste sur données sales

  • Deux modes annoncés clairement : MCP Stripe/PayPal présent → litiges, motifs et deadlines autoritaires ; sinon mode Qonto pur — débits de reprise (dispute / chargeback / reversal + variantes FR), souvent doublés d'un débit de frais du même PSP le même jour
  • Piège Stripe assumé : le litige est souvent compensé dans le payout suivant — pas de ligne séparée. Le skill signale les payouts anormalement bas comme candidats et recommande le MCP Stripe, plutôt que de deviner
  • Rapprochement carte sur emitted_at, pas settled_at (1-2 jours d'écart)
  • Pièce manquante → listée comme manquante avec où la chercher — une checklist, pas un haussement d'épaules
  • Aucun litige trouvé → le skill le dit et n'en invente jamais ; deadlines inconnues → fenêtres types indicatives + renvoi au portail
  • Pagination ≤ 50 partout · list_transaction_attachments vérifié avant d'annoncer un upload réussi

🏗 Schéma fonctionnel

🔒

Le modèle d'intégrité : le mémo attaché est une synthèse datée qui cite les pièces sources (système · identifiant · date · ce que la pièce prouve) — jamais un justificatif fabriqué. Et la soumission de la défense reste humaine : le skill prépare tout, l'utilisateur soumet sur le portail Stripe/PayPal. Jamais présentée comme déposée.

🎬 Vidéo de démo

La démo ≤ 3 min jointe à la PR suit le storyboard : le problème (l'argent repris + frais + deadline) → détection → dossier 4 pièces assemblé et sourcé → mémo attaché à la transaction → « tu n'as plus qu'à soumettre ». Le script détaillé de tournage est conservé en interne (hors dépôt).

🛡 Garde-fous

  • Jamais de pièce fabriquée : le mémo est une synthèse datée qui cite les originaux — la distinction est écrite dedans
  • Jamais « réponse soumise » ni « litige gagné » : la soumission se fait sur le portail Stripe/PayPal, par l'utilisateur
  • Deadlines = celles du litige ; les fenêtres génériques sont toujours étiquetées indicatives
  • Upload uniquement avec consentement explicite, annoncé après confirmation par list_transaction_attachments
  • IBAN masqués (4 derniers chiffres) · pagination ≤ 50 · tous les montants d'exemple sont inventés
